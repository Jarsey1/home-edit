# V2.1 Data Persistence Assessment

Inspected: October 29, 2026

## Executive summary

The app has two persistence layers:

1. **Supabase** for the original shared dataset and, once the additive migrations
   are applied, V2/V2.1 records.
2. **Browser `localStorage`** (`next-home-edit:data:v3`) as the fallback and as
   the current store for V2/V2.1 data while the new tables are absent.

The live Supabase project currently has the original tables but **not** the V2
tables. That is why the More screen says wishlists, photos, plans and
evaluations are on this device only. No local data was deleted or migrated.

## Supabase verification

- Original tables reachable: `homes` (3 rows), `wishlist_items` (72),
  `budget_settings` (1), `comparison_notes` (2), `tour_notes` (0).
- V2 endpoints `wishlists`, `wishlist_requirements`, `property_details`,
  `budget_scenarios` return **404** until `0002_v2.sql` is run.
- `property_evaluations` returns **404** until `0003_evaluations.sql` is run.
- RLS on the original and new tables is currently permissive for the
  `anon`/`authenticated` roles (`using (true)`), matching the original
  single-household design.
- `owner_id` is always `shared` in the current build.
- No Supabase Auth session is used. The client disables session persistence.
- No Supabase Storage bucket is used. No service-role key is present in the
  frontend; only the publishable/anon key is exposed.
- Auth-ready policies are included as comments in `0002` and `0003`.

## Safe migration strategy

1. **Back up local data first.** In Safari/Chrome developer tools copy
   `localStorage.getItem('next-home-edit:data:v3')` to a file. Keep the original.
2. Apply `supabase/migrations/0002_v2.sql`, then
   `0003_evaluations.sql`, in the Supabase SQL editor during low use.
3. Reload the app. The More screen should change from device-only to synced.
4. Verify counts in Supabase and confirm the app still reads the original
   `homes` and `tour_notes` rows.
5. Do not clear `localStorage` yet. Keep it as a rollback copy until the synced
   data has been verified.
6. Only then enable Supabase Auth. Migrate legacy `owner_id='shared'` rows to
   real user IDs with an explicit, reviewed SQL script; then activate the
   auth-ready RLS policies.

## Risks and notes

- Local V2/V2.1 records are not automatically uploaded when the migrations are
  first applied. This is intentional: no automatic migration. Back up and move
  them deliberately if needed.
- A missing `0003` while `0002` exists means wishlists/photos/plans sync but
  evaluations stay local. The More screen reports this separately.
- Photos are data URLs, not Storage objects. They are suitable for a shortlist,
  not a large library.
- True per-account isolation is not enforced until Supabase Auth and the
  auth-ready RLS policies are activated.


## Compare Homes data flow (verified October 29, 2026)

The comparison screen reported "not enough information" for homes that already
had bedrooms, bathrooms and prices. The cause was **not** missing property
facts and **not** a stale score cache:

1. `scoreRequirements()` only includes requirements where
   `configured !== false`; drafts are intentionally skipped.
2. Most existing wishlist requirements are still drafts, so the active
   wishlist had no scoreable requirements. The provider correctly returned an
   empty/insufficient result.
3. Property facts map through `factsFromHome()`. Canonical `homes` columns
   (`price`, `beds`, `baths`, `sqft`, `yearBuilt`, `city`, `type`, `hoa`,
   `pool`, `gated`) win over cached `property_details.facts`; details fill the
   remaining keys. So an edited bedroom count or price is used immediately.
4. `scoredHomes` is derived from current provider state on every render. There
   is no persisted score cache, so scores cannot be stale in storage.

Fixes now make that state explicit and actionable:

- Match status distinguishes **Wishlist not ready**, **Partially evaluated**,
  **Scored** and **Disqualified**.
- A draft count explains why nothing is scoreable without auto-activating
  drafts.
- **View Missing Information** opens a per-home checklist built from
  configured **and** draft requirements (excluding `ignore`). Each row shows
  the requirement, required condition, known property value, status and a
  direct action.
- Known facts are evaluated automatically; users are never asked to re-enter
  a known value. Unknown facts link to property details, and incomplete
  requirements link to the Wishlist tab.
- Coverage and unknown dealbreakers prevent a property from being labelled
  fully scored. The scoring formula and weights are unchanged.

## Where each piece of data is stored today

- **Address, purchase price, beds, baths, sqft, lot, garage, pool, gated, HOA,
  year built, property type, description, features:** `homes` in the shared
  Supabase dataset. If Supabase is unreachable, the last snapshot also exists
  in `localStorage`.
- **Property photos, listing URL, private notes, favorite flag, extra facts,
  tour date/status:** `property_details` once `0002` is applied. Today those
  rows are not available, so they live in the `localStorage` snapshot
  `next-home-edit:data:v3` (legacy key: `next-home-edit:data`).
- **Wishlists and wishlist requirements:** `wishlists` and
  `wishlist_requirements` once `0002` exists; otherwise only
  `next-home-edit:data:v3`.
- **Property evaluations:** `property_evaluations` once `0003` exists;
  otherwise only `next-home-edit:data:v3`. Evaluations are keyed by
  `home + wishlist + requirement`, so switching wishlists recalculates without
  losing answers.
- **Budget scenarios and confirmation:** `budget_scenarios` (including
  `confirmed` after `0003`); otherwise local snapshot.
- **Tour notes and comparison notes:** shared Supabase `tour_notes` and
  `comparison_notes`; also mirrored locally.
- **Language:** `nhe-lang` cookie only.
- **IndexedDB:** not used anywhere. There is exactly one application storage
  key: `next-home-edit:data:v3` in `window.localStorage`.

Why local: the V2/V2.1 tables and the Supabase Storage bucket do not exist in
the live project yet. The client writes to Supabase only when the relevant
table is reachable; otherwise it keeps the record on the device and the More
and Wishlist screens say so. No operation ever claims account sync when the
write did not succeed.

## Secure Supabase synchronization plan (designed, not implemented)

This plan requires approval before any table, policy, bucket or data migration
is changed. It is deliberately not wired into the current build; the shared
`owner_id = 'shared'` dataset and permissive `using (true)` policies must not
receive private data.

### 1. Authentication and ownership

- Enable Supabase Auth (email magic link or OTP first; no paid provider).
- Add `profiles (id uuid primary key references auth.users on delete cascade,
  display_name text, created_at timestamptz default now())`.
- Every user-owned row gets `owner_id uuid not null references auth.users(id)
  on delete cascade default auth.uid()`.
- The client must use the authenticated session; the publishable key stays the
  only key in the frontend. No service-role key.

### 2. Tables to create or convert

| Table | Ownership key | Notes |
| --- | --- | --- |
| `homes` | `owner_id` | Convert from shared list; do not overwrite legacy rows |
| `property_details` | `owner_id`, unique `(owner_id, home_id)` | Facts, notes, listing URL |
| `property_evaluations` | `owner_id`, unique `(owner_id, home_id, wishlist_id, requirement_id)` | Append/upsert, never destructive |
| `wishlists` | `owner_id` | User-created lists |
| `wishlist_requirements` | via `wishlist_id` owner | Reusable templates stay user-owned |
| `budget_scenarios` | `owner_id`, unique `(owner_id, home_id, wishlist_id)` | Includes `confirmed` |
| `tour_notes` | `owner_id` | Convert from shared |
| `comparison_notes` | `owner_id` | Convert from shared |

Use one migration that adds nullable `owner_id` first, backfills only after an
explicit ownership decision, then sets `not null` and enables RLS.

### 3. Row Level Security shape

For every user-owned table:

```sql
alter table public.<table> enable row level security;

create policy "<table> select own" on public.<table>
  for select using (owner_id = auth.uid());

create policy "<table> insert own" on public.<table>
  for insert with check (owner_id = auth.uid());

create policy "<table> update own" on public.<table>
  for update using (owner_id = auth.uid())
  with check (owner_id = auth.uid());

create policy "<table> delete own" on public.<table>
  for delete using (owner_id = auth.uid());
```

`wishlist_requirements` must also verify the parent wishlist belongs to the
caller (`exists (select 1 from wishlists w where w.id = wishlist_id and
w.owner_id = auth.uid())`). Keep policies per operation so `anon` gets no
access.

### 4. Supabase Storage for photos

- Private bucket `property-photos` (`public = false`).
- Object path: `<user_id>/<home_id>/<photo_id>.jpg`.
- Storage policies: select/insert/update/delete only when
  `(storage.foldername(name))[1] = auth.uid()::text`.
- Store the object path in `property_details.photo_path`, not a data URL.
- Read with short-lived signed URLs; keep the local compressed preview as an
  offline fallback only.

### 5. Migration and verification sequence

1. Capture a local backup of `next-home-edit:data:v3` per device.
2. Export current Supabase rows (`homes`, `wishlist_items`, notes) to files.
3. Apply additive migrations with nullable `owner_id` and no RLS change yet.
4. Add Auth and have each owner claim their rows explicitly.
5. Backfill `owner_id`; verify counts before enabling RLS.
6. Enable RLS and the Storage bucket policies.
7. Test two accounts: each sees only their own homes, details, photos,
   evaluations, notes and budget scenarios; direct REST reads with the other
   user's JWT return zero rows.
8. Test offline/error paths: failed writes keep local data and show the
   device-only confirmation. No silent uploads.

Until steps 1–6 are approved and completed, the application remains
device-local for V2/V2.1 data and continues to state that plainly.
